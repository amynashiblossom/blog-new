# 위매칭 2차 스프린트 정리 및 1차 위솝 회의 자료 준비

> 작성일: 2026-09-15 · Team K

---

## 1. 프로젝트 개요

**서비스명**: 위매칭
**핵심 문구(프로젝트명, 고정)**: `근무종료 1시간 후 급여지급 일감 × N잡러 매칭`
**청중용 헤드라인(구어체)**: "퇴근 1시간 뒤, 통장에 꽂히는 일감을 잇습니다"

**출발점**: 위솝(WESOP)이 이미 보유한 매장-직원 데이터 자산(샵솔/프랜솔)과, 2021년 위솝이 제시했던 '긱이코노미 번개채용' 아이디어에서 착안. 이번 프로젝트는 그 아이디어를 근로자용 서비스로 구체화한 결과물.

**주의 표현**: "급구"라는 단어는 시장 최강자(당근알바)를 직접 연상시키므로 서비스 설명 어디에도 사용하지 않음. 대신 "일감", "N잡러", "매칭" 등의 표현을 사용.

## 2. 문제정의 (두 축)

이용자가 지원을 망설이는 이유를 아래 두 가지로 뾰족하게 정의함.

1. **근무 종료 시간이 명확하지 않다** — 언제 끝나는지, 총 몇 시간 일하는 건지 정보가 들쭉날쭉하면 지원을 망설이게 됨
2. **돈이 언제 들어오는지 모른다** — 급여가 '언젠가'가 아니라 '정확히 언제' 들어오는지 알아야 안심하고 지원함

이 두 가설을 검증하기 위해 **Case 1(개선안)**과 **Case 2(기존 방식)** 두 버전을 만들어 UT로 비교함.

| 구분 | Case 1 | Case 2 |
|---|---|---|
| 근무시간 표시 | 모든 일감에 항상 표시 (예: "18:00~22:00(4시간)") | 일부 카드에서 생략되거나 시간 계산이 부정확 |
| 급여 지급 시점 | "근무종료 후 1시간 후 급여지급" (상대적 즉시 약속) | "급여지급예정일: 2026.09.09(수)" (특정 날짜 고정) |
| 지원완료/채용완료 화면 | 동일 | 동일 (차이 없음) |

## 3. UT 결과 요약

> ⚠️ 아래는 대화 중 여러 차례 정정된 수치입니다. 최종 발표 전 팀 내부에서 인원수 breakdown을 한 번 더 교차 확인 권장.

### 3-1. 제안서(위솝용)에 반영된 UT 데이터 — 총 12명 기준

- **참여자 구성(12명)**: 급구 경험 6명 · 당근 경험 2명 · N잡 관심 낮은 정기 알바 이용자 2명 · 과거 N잡 경험자(일러스트레이터) 1명 · 급구 비경험자 1명
- 전체 인터뷰 응답자는 14명이었으나, 이 중 유의미한 응답을 준 12명을 기준으로 분석함

| 검증 항목 | 결과 | 비고 |
|---|---|---|
| 근무 종료 시간 명확화 | **7 / 12** 긍정 | 급구·당근 경험자 8명 모두 언급, 정기 알바 근무자에게도 영향 |
| 근무종료 1시간 후 급여지급 | **8 / 12** 긍정 | 급구·당근 경험자 8명이 지원 결정 요소로 꼽음. 정기 알바 이용자 1명은 관심 낮음 |
| 급구와의 유사성 | 질문 대상 11명 중 **10명 "유사하지 않다"** / 1명 "비슷하다" | 나머지 1명은 급구를 몰라 질문 자체를 하지 않음 |

**유사하지 않다는 근거**: 색감이 급구의 파란색과 다름 / 리스트형 UI는 일반적인 형태로 인식

**유의할 점(리스크, 균형을 위해 그대로 반영)**:
- 급구 경험자 1명: 화면이 다소 복잡해 보인다는 의견
- 당근 경험자 1명: 실제 지원 여부는 서비스 인지도에 달려 있다는 의견

**대응 정책(제안서 스코프에 반영)**: 급구와의 차별성을 더 확실히 하기 위해, 당일 미지급 일감도 지급예정일을 반드시 명시하고, 미준수 5회 누적 시 일감 등록을 제한하는 정책을 이번 제안 범위에 포함.

### 3-2. 2차 UT (9/14 진행) — 별도 라운드

- **참여자(14명 언급)**: 9/14 실제 급구로 뽑혀 온 6명, 9/14 실제 당근으로 뽑혀 온 2명, 일감기반 근무 관심 낮은 4명, 알바몬형 정기(월·화) 근무 1명
  - ⚠️ 합산 시 13명으로 집계됨(6+2+4+1). "총 14명"과 1명 차이 — 팀 내부 재확인 필요.

### 3-3. 3차 회귀 테스트 (9/15 진행 예정)

- 어제(9/14) '일감기반 근무 관심 낮은' 그룹 중 **1명 회귀** (같은 사람 재진행, 신규 인원 아님)
- **신규 1명** 추가 (일감기반 근무 관심 낮은 세그먼트)

**카운트 정리 원칙**: 회귀 테스트는 세션 수에는 포함되지만 고유 참여자 수에는 중복 카운트하지 않음.

| 구분 | 값 |
|---|---|
| 고유 참여자 수 | 14명(기존) + 1명(신규) = **15명** |
| 총 세션(진행 횟수) | 14회(기존) + 2회(오늘 회귀 1 + 신규 1) = **16회** |

**중요**: 이번 위솝 실무미팅 제안서는 **9/14 기준 14명 데이터까지만** 사용하고, 9/15 회귀·신규 인원은 반영하지 않기로 결정함.

## 4. 스코프 설계 (Phase 구분)

**판단 기준**: "개발 리소스와 법적 리스크가 큰가?" → 그렇다면 화면(UX) 설계로 대체하고 다음 단계로 이관

| Phase | 내용 | 비고 |
|---|---|---|
| **Phase 1 (이번 제안 · 시연 범위)** | 근로자용 매칭 퍼널 완결 — 일감 탐색 → 지원 → 매칭 → 근무완료, '지급대기' 상태 UI + 타임스탬프, 정상/예외 케이스 State Table, **지급예정일 명시 + 미준수 5회 누적 시 등록 제한 정책** | 오늘 실제로 시연하는 범위 |
| **Phase 2 (제안만, 공동개발 아님)** | 급여 정산 엔진 — 매장 선입금 → 원천세 자동 공제 → 오픈뱅킹 실계좌 이체, 지급명세서 자동 발급 | ⚠️ Team K가 함께 만들 계획은 없음. "이 방향으로 확장하시길 제안"하는 수준으로만 톤 조정 완료 |
| **Phase 3 (확장 제안)** | 고용주 통합 대시보드, 근태 기록 기반 평판 점수제 | |

**Phase 2를 별도 단계로 분리한 근거**: 일반 커머스 예치금(예: 당근페이)과 달리, 급여는 근로기준법상 통화로 근로자 본인 계좌에 직접·전액 지급되어야 하는 법적 요건이 있어 원천세 공제·실계좌이체 로직이 필요함. 이를 "당근 예치금 구조를 베낀 것 아니냐"는 질문에 대한 방어 논리로 활용.
